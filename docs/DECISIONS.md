## DEC-002：采用 Raspberry Pi 与 Arduino 分层控制

- 日期：2026-10-13
- 决策：Raspberry Pi 运行网页、多媒体和高级逻辑；Arduino Uno 负责串口解析、电机与舵机实时控制；Motor Shield 驱动直流电机，PCA9685 驱动舵机。
- 原因：该结构已由 README、接线图和代码实际实现；职责清晰，复现风险较低。
- 放弃方案：只用 Raspberry Pi 直接控制全部执行器；只用 Arduino 承担网页与音频。
- 影响：需要两套开发/运行环境和 USB 串口；电源需分域并共地。
- 状态：已采用，硬件型号待采购确认。

## DEC-003：Arduino 首版不使用 FreeRTOS

- 日期：2026-10-13
- 决策：保留现有裸机 `loop()`、非阻塞串口、定时更新和动作队列架构。
- 原因：代码已能调度当前功能；Uno SRAM有限，引入 RTOS 会增加栈和并发风险，首版没有证明必须使用 RTOS 的需求。
- 放弃方案：在 Uno 上增加 FreeRTOS 任务；立即迁移到 ESP32/STM32。
- 影响：新增功能应继续避免阻塞；若未来加入高频传感器、编码器闭环等，再重新评估控制器与调度方案。
- 状态：已采用。

## DEC-004：Arduino IDE 与 VS Code 分工

- 日期：2026-10-13
- 决策：使用 Arduino IDE 编译/烧录 `.ino`；使用 VS Code 编辑仓库并通过 Remote SSH 维护树莓派端。
- 原因：贴合原项目说明，降低首版工具链复杂度；用户主要使用 C 与 Python。
- 放弃方案：首版迁移 PlatformIO；为前端引入 Node 构建系统。
- 影响：必须记录 Arduino 库版本和树莓派软件版本，避免环境不可复现。
- 状态：计划采用，软件尚待安装确认。

## DEC-005：3D打印使用 STL，修改使用 STEP + Fusion

- 日期：2026-10-13
- 决策：原始零件直接使用作者 STL 切片；需要改变孔位、支架或拆分时，在 Fusion 中导入 STEP 修改。
- 原因：作者公开 STL 和 STEP；STEP 保留实体几何且 Fusion 可处理，不需要依赖 SolidWorks。
- 放弃方案：仅编辑 STL 网格；为打开模型专门购买/安装 SolidWorks。
- 影响：导入的 STEP 不包含原 SolidWorks 特征历史；每个修改件应记录来源、尺寸变化和导出参数。
- 状态：已决定，模型下载与兼容验证待完成。

## DEC-006：先复现稳定基础功能，再增加语言模型

- 日期：2026-10-13
- 决策：首版优先完成行走、游戏手柄、七舵机、音频和预设/随机动作；语音聊天与语言模型放到后续阶段。
- 原因：机械装配、供电和台架可靠性是当前主要风险；对话功能可以在 Raspberry Pi 端独立扩展。
- 放弃方案：在底盘和供电未验证前并行开发完整连续语音助手；在 Pi 4B 上强制运行大型离线模型。
- 影响：提前预留 USB 麦克风和扬声器接口；未来 LLM 只能通过白名单动作层控制机器人，不能直接发送任意串口命令。
- 状态：已采用。

## DEC-007：采购前先完成规格核验和电源预算

- 日期：2026-10-13
- 决策：模型、软件、BOM 与控制器采购作为下一阶段 P0；电机轴尺寸/电流、驱动余量、舵机电源和连接器必须在下单前确认。
- 原因：错误的37mm减速电机、Motor Shield兼容性或虚标降压模块会直接导致装配失败和安全风险。
- 放弃方案：按通用名称直接购买、到货后再调整。
- 影响：采购任务必须产生可核验规格、供应商链接、数量、备用量和到货测试项。
- 状态：进行中。
